# OPC 技术架构说明

> 说明系统如何分层、模块如何协作，以及问培风为何采用「Express 网关 + Python 模型服务」结构。

---

## 1. 总体架构

```text
┌──────────────────────────────────────────────┐
│  浏览器 / 手机浏览器                           │
│  opc-web (React + TS + Vite)                 │
│  请求前缀：/api  + Authorization: Bearer JWT │
└──────────────────────┬───────────────────────┘
                       │ HTTP
         ┌─────────────▼─────────────┐
         │  Nginx（生产）             │
         │  / → 静态 dist            │
         │  /api → 127.0.0.1:8080    │
         └─────────────┬─────────────┘
                       │
         ┌─────────────▼─────────────┐
         │  opc-server (Express)     │
         │  鉴权 / 业务 / 落库 / AI网关│
         └──────┬──────────────┬─────┘
                │              │
     ┌──────────▼──────┐   ┌───▼────────────────┐
     │ MySQL 8         │   │ opc-aiservices      │
     │ Prisma 访问     │   │ FastAPI + 大模型    │
     └─────────────────┘   └────────────────────┘
```

| 进程 | 默认端口 | 职责 |
|------|----------|------|
| opc-web 开发服务器 | 5173 | 开发态；`/api` 代理到 8080 |
| opc-server | 8080 | 业务 API |
| opc-aiservices | 8000 | 大模型调用（建议仅本机） |
| MySQL | 3306 | 持久化 |
| Nginx | 80 | 生产入口 |

## 2. 前端架构（opc-web）

### 2.1 技术选型

| 技术 | 用途 |
|------|------|
| React + TypeScript | UI 与类型约束 |
| Vite | 开发与构建 |
| React Router | 多页面路由 |
| Ant Design Mobile | 移动端组件风格 |
| Axios | HTTP 客户端 |

### 2.2 目录要点

```text
opc-web/src/
├── api/           # 按领域封装接口（auth、projects、ai…）
├── pages/         # 页面
├── layouts/       # AppLayout（Tab + 问 AI 入口）
├── components/    # RequireAuth 等
└── main.tsx / App.tsx
```

### 2.3 请求约定

- `baseURL: '/api'`（见 `api/client.ts`）  
- 开发：Vite proxy → `http://localhost:8080`  
- 生产：Nginx 把 `/api` 转到 Express  
- Token 存 `localStorage`，请求头带 `Authorization: Bearer <token>`  
- 统一响应：`{ code, message, data }`，成功一般 `code === 0`  

### 2.4 主要路由（示意）

| 路径 | 页面 |
|------|------|
| `/login` `/register` | 登录注册 |
| `/discover` | 发现 |
| `/publish` `/publish/:id` | 发布 / 编辑草稿 |
| `/project` | 我的项目 Tab |
| `/projects/:id` | 项目详情 |
| `/message` `/message/:id` | 消息 / 聊天 |
| `/profile` … | 我的及相关子页 |
| `/assistant` | 问培风 |

## 3. 业务后端架构（opc-server）

### 3.1 技术选型

| 技术 | 用途 |
|------|------|
| Node.js + Express + TypeScript | HTTP API |
| Prisma | ORM，映射 MySQL |
| JWT + bcryptjs | 登录态与密码哈希 |
| dotenv | 环境变量 |

### 3.2 分层习惯

```text
routes/        # 路由与参数校验、调用 service
services/      # 稍复杂的业务（项目详情、会话保证等）
middleware/    # requireAuth、错误处理
utils/         # DTO、响应 ok/fail、body 解析
prisma/        # schema.prisma
```

### 3.3 模块与挂载

`routes/index.ts` 将各路由挂到 `/api` 下，例如：

- `/api/auth/*`  
- `/api/projects/*`、`/api/tasks/*`  
- `/api/applications*`、`/api/favorites/*`  
- `/api/conversations/*`  
- `/api/ai/*`  
- `/api/health`  

### 3.4 AI 网关职责

`routes/ai.ts`：

1. `requireAuth`  
2. 校验 `content`  
3. 请求 Python：`POST {AI_SERVICE_URL}/api/ai/chat`，body 为 `{ messages, stream:false }`  
4. 写入 `ai_chats`（user + assistant）  
5. 返回前端契约：`reply`、`suggestions`、消息 DTO  

这样前端只认 Express 契约；密钥与厂商差异隔离在 Python 侧。

## 4. AI 服务架构（opc-aiservices）

### 4.1 技术选型

| 技术 | 用途 |
|------|------|
| FastAPI | HTTP 服务 |
| AsyncOpenAI | 调用兼容 OpenAI 的网关 |
| python-dotenv | 读取密钥 |

### 4.2 接口

| 路径 | 说明 |
|------|------|
| `GET /health` | 健康检查、是否配置 Key |
| `POST /api/ai/chat` | `stream:false` → `{ reply }`；`true` → SSE |

系统提示词将助手人设为「培风」，面向大学生项目协作场景。

### 4.3 配置

环境变量：`OPENAI_API_KEY`、`OPENAI_BASE_URL`、`OPENAI_MODEL`  
**禁止**把真实 Key 提交进 Git。

## 5. 数据架构

- SQL 脚本权威副本：`One-Person-Campany/sql/`  
- Prisma：`opc-server/prisma/schema.prisma`  
- 核心表：用户、项目、成员、申请、任务、会话、消息、收藏、`ai_chats` 等  

改表流程建议：先改 `One-Person-Campany/sql/` 与 `opc-server/prisma`，再 migrate/push，前后端字段对齐。

表结构以建表脚本与 Prisma schema 为准（仓库内不再单独维护「数据库设计」文档）。

## 6. 关键时序

### 6.1 登录

```text
前端 POST /api/auth/login
  → Express 校验手机号密码
  → 签发 JWT
  → 前端存 token，后续请求携带
```

### 6.2 申请加入项目

```text
申请人 POST /api/projects/:id/applications
  → 写入 pending 申请
  → 「项目-待确认」可见；「进行中」仍无
发布者 PATCH 审核 approved
  → 写入 project_members
  → 申请人进入「进行中」
  → 可确保项目会话成员
```

### 6.3 问培风

```text
前端 POST /api/ai/chat { content }
  → Express 鉴权
  → Python /api/ai/chat { messages, stream:false }
  → 大模型
  → { reply }
  → Express 落库 ai_chats
  → 前端展示
```

## 8. 设计取舍（答辩可讲）

1. **为何不前端直连大模型？**  
   密钥安全、统一鉴权与落库、响应格式与业务一致、便于注入站内数据。  

2. **为何 AI 单独 Python 服务？**  
   Python 生态调用模型方便；与 Node 业务解耦，可独立扩缩与替换厂商。  

3. **为何生产用 Nginx？**  
   静态资源与 API 同域，避免 CORS 麻烦；统一 80 入口，隐藏内部端口。
